⚠️ The Real-World Problem

In technical institutions, faculty members struggle with massive administrative overhead:

  • Fragmented Tracking: Assignments and proofs are scattered across Google Classrooms, WhatsApp groups, and spreadsheets.
  • No Real-time Coding Visibility: Manually verifying 350+ student LeetCode profiles and GitHub commits every night is impossible.
  • Delayed Notifications: Students miss assignment deadlines because web portals lack proactive instant alerts.
  • Disconnected Student Portfolios: Placement coordinators lack verified student resumes, project links, and skill matrices in one place.

💡 The Engineered Solution

IT TaskManager is a unified, end-to-end departmental operating system:

  • Automated Coding Engine: Scrapes LeetCode submissions via GraphQL and GitHub commits via REST APIs in IST timezone without hitting rate limits.
  • 4-Tier Target Hierarchy: Enforces dynamic daily/weekly coding targets from Student → Class → Year → Department levels.
  • Telegram Bot System: Provides instant student lookups (`/check <reg_no>`), class summaries (`/3ita`), and daily broadcasts.
  • Dual-Mode Git Backups: Auto-commits student directory backups and takes 24-hour rolling PostgreSQL database snapshots directly to GitHub.

4. Module-by-Module Technical Breakdown

Deep dive into data flows, database relations, and APIs for every core module.

👥 Module 2: In-Memory RAM Directory Cache & Dual-Mode Git Sync ▼

A. What is it? A high-speed in-memory indexing engine in studentDirectoryService.ts that keeps all 368+ student profiles loaded in Node.js RAM Maps (constantStudentByIdMap, constantStudentByRegNoMap), dropping profile lookup times from ~30ms to under 0.01ms.

B. Why did we build it? To enable instantaneous Telegram bot responses and eliminate redundant database queries during batch coding syncs.

C. Dual-Mode Git Sync: Automatically serializes student directories into Year and Section CSV/JSON files (students_directory/Year_2/Section_A.csv) and pushes updates to GitHub using the GitHub Contents REST API (on cloud containers) or Git CLI (locally).

studentDirectoryService.ts snippet
// Pre-indexed RAM cache maps
export const constantStudentByIdMap = new Map<string, StudentDirectoryEntry>();
export const constantStudentByRegNoMap = new Map<string, StudentDirectoryEntry>();

export function getStudentFromDirectoryByRegNo(regNo: string): StudentDirectoryEntry | null {
  return constantStudentByRegNoMap.get(regNo.trim().toUpperCase()) || null;
}

🔍 Rate Limit & Concurrency Architecture

  • Authenticated Quota: GitHub provides 5,000 requests/hour with a single Personal Access Token (`GITHUB_TOKEN`).
  • 350 Student Requirement: Syncing 350 students requires exactly 350 API calls (only 7% of hourly quota).
  • Batch Worker: Requests are processed in batches with a concurrency limit of 5-8 requests to prevent socket exhaustion.
  • Offline Fallback: If rate limits are ever exceeded, the system serves the last cached count from github_daily_commits without throwing UI errors.

🏆 Real-Time Top 3 Leaderboard

The frontend dynamically sorts students by daily/weekly commit counts using useMemo:

Leaderboard calculation snippet
const githubTop3 = useMemo(() => {
  const isDaily = leetcodeViewType === 'DAILY';
  return [...githubProgressList]
    .filter(s => (isDaily ? s.commitsToday : s.commitsThisWeek) > 0)
    .sort((a, b) => (isDaily ? b.commitsToday - a.commitsToday : b.commitsThisWeek - a.commitsThisWeek))
    .slice(0, 3);
}, [githubProgressList, leetcodeViewType]);

10. Authentication, RBAC & Data Protection

Defending against SQL Injection, XSS, Brute Force, and Privilege Escalation.

🛡️ 100% Parameterized SQL

Every SQL query across 29 tables uses strict positional placeholders ($1, $2), completely preventing SQL Injection.

🔐 Role-Based Access Control

Strict hierarchy guard: SUPREME_ADMIN → HOD → CLASS_ADVISOR → STUDENT with year-scope database query filters.

✨ Input Trimming & Sanitization

All URLs and usernames are sanitized using .trim() before saving, preventing corrupted directory or database entries.

Technology Defense

17. Why This Technology? Comparative Defense

Defending our technical choices against popular alternatives during viva questioning.

⚛️ React 19 + TypeScript

Why Selected: Fast client rendering, singlefile inlining, compile-time type safety.

Alternative: Angular / Vue.js

Why Rejected: Angular has heavy enterprise boilerplate; Vue lacks rich OpenXML ExcelJS integrations.

🐘 PostgreSQL + Supabase

Why Selected: Strict relational integrity, foreign key cascades, compound indexing.

Alternative: MongoDB / NoSQL

Why Rejected: Academic workflows are relational; NoSQL creates orphaned records upon class deletions.

🤖 Telegram Bot API

Why Selected: Zero-cost push delivery, instant long-polling response (< 150ms).

Alternative: WhatsApp Business API / SMS

Why Rejected: WhatsApp charges recurring per-message fees and requires Facebook enterprise verification.
